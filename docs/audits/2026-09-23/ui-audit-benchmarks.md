# Knowledge Crib UI audit: external benchmarks

Research date: 2026-09-23. Scope: current primary sources for accessibility, enterprise design systems, and human–AI interaction. This is an **audit rubric**, not a finding that Knowledge Crib passes or fails any item. WCAG 2.2 Level AA is the accessibility conformance target used here; Carbon, USWDS, Microsoft HAX, and Google People + AI supply design guidance rather than binding requirements. A browser and assistive-technology review must establish product findings.

## Accessibility acceptance checks

| Audit area | Check in the running UI | Primary source |
| --- | --- | --- |
| Text and controls | Measure ordinary text at **4.5:1**, large text at **3:1**, and the visual information needed to identify active controls and states at **3:1**. Check every theme, hover, selected, and error state. Review disabled-state legibility as a usability concern; WCAG's inactive-component exceptions mean it is not an automatic contrast failure. Color must not be the sole cue for state or meaning. | [WCAG 2.2, 1.4.3, 1.4.11, 1.4.1](https://www.w3.org/TR/WCAG22/#visual-audio-contrast); [Carbon color guidance](https://carbondesignsystem.com/guidelines/accessibility/color/) |
| Keyboard and focus | Complete every task without a pointer; verify logical focus order, a visible focus indicator, and no focused control entirely hidden by sticky UI. Test modal focus entry, containment, Escape, and return; test tab lists and comboboxes with their documented keys. | [WCAG 2.2, 2.1.1, 2.4.3, 2.4.7, 2.4.11](https://www.w3.org/TR/WCAG22/#operable); [APG dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/), [combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) |
| Magnification and pointer | At a 320 CSS-pixel viewport or 400% zoom on a 1280-pixel viewport, ensure no loss of information or functionality and no two-dimensional scrolling except where essential. Provide a single-pointer alternative to dragging. Check the **24 × 24 CSS-pixel** minimum target rule and its specified exceptions. | [WCAG 2.2, 1.4.10, 2.5.7, 2.5.8](https://www.w3.org/TR/WCAG22/) |
| Status and errors | Announce asynchronous result counts, saved-state changes, errors, and success messages to assistive technology without moving focus. Identify errors in text and make recovery understandable; use status versus alert urgency appropriately. | [WCAG 2.2, 3.3.1 and 4.1.3](https://www.w3.org/TR/WCAG22/); [USWDS alert accessibility](https://designsystem.digital.gov/components/alert/) |
| Graphs and diagrams | Give the knowledge graph a short identifying description and a textual representation of its essential information and relationships. Ensure its key actions and information remain available through keyboard-accessible controls or a structured alternative. | [W3C WAI complex images tutorial](https://www.w3.org/WAI/tutorials/images/complex/); [WCAG 2.2, 1.1.1 and 2.1.1](https://www.w3.org/TR/WCAG22/) |

**Scoring caution:** Focus Appearance (2.4.13) is **AAA** in WCAG 2.2; visible focus (2.4.7) and focus not obscured minimum (2.4.11) are **AA**. Do not report the AAA criterion as an AA failure. [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

## Design system and journey checks

| Audit area | Check in the running UI | Primary source |
| --- | --- | --- |
| Theme architecture | Inventory semantic tokens for foreground, surface, border, focus, interactive, and status roles across light/dark themes. Check that components use tokens consistently and each pairing meets contrast needs. This is a maintainability and consistency benchmark, not a mandate to adopt Carbon or USWDS tokens. | [Carbon themes](https://carbondesignsystem.com/elements/themes/overview/); [USWDS theme tokens](https://designsystem.digital.gov/design-tokens/color/theme-tokens/); [Carbon component checklist](https://carbondesignsystem.com/contributing/component-checklist/) |
| Visual hierarchy | Audit whether typography and spacing follow a small, role-based scale so page title, section title, data, supporting text, and actions remain distinguishable. Check density at narrow and wide layouts. | [Carbon themes and type tokens](https://carbondesignsystem.com/elements/themes/overview/); [Carbon spacing scale](https://carbondesignsystem.com/elements/spacing/overview/) |
| Empty, loading, and failure states | Distinguish first use, zero search results, filtered-out results, no permission, configuration needed, and service failure. Each state should say what happened and offer the next useful action where one exists. | [Carbon empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/); [Carbon notification usage](https://carbondesignsystem.com/components/notification/usage/) |
| Feedback | Use contextual, brief status messages for routine events. Error messages should identify the failed action and a recovery step; persistent action-required notices must remain available long enough to act. Use status text or icon as well as color. | [Carbon notification usage](https://carbondesignsystem.com/components/notification/usage/); [USWDS alert](https://designsystem.digital.gov/components/alert/) |

## AI and RAG trust checks

These are **audit inferences** from first-party human–AI guidance, applied to Knowledge Crib's memory and code-context surfaces. They are not claims that those sources prescribe a specific RAG layout.

| Audit area | Check in the running UI | Primary source |
| --- | --- | --- |
| Scope and provenance | For a returned memory or code claim, show the user which repository/principal scope and source it came from, the evidence they can inspect, and whether it is current, degraded, pending, or needs review. A claim with missing or weak evidence should not look identical to an admissible current claim. | [Google People + AI, Explainability + Trust](https://pair.withgoogle.com/chapter/explainability-trust); [Microsoft HAX G11, explain behavior](https://www.microsoft.com/en-us/haxtoolkit/guideline/make-clear-why-the-system-did-what-it-did/); [NIST GenAI Profile, provenance](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) |
| Expectation calibration | State what the system can and cannot infer from its index and ledger at the point of use. When coverage is incomplete or a source is stale, say so near the result; avoid unvalidated numerical confidence badges. If numeric confidence is considered, test user understanding first. | [Microsoft HAX G2, communicate performance](https://www.microsoft.com/en-us/haxtoolkit/guideline/make-clear-how-well-the-system-can-do-what-it-can-do/); [Google People + AI, confidence displays](https://pair.withgoogle.com/chapter/explainability-trust) |
| Uncertainty and zero evidence | Check the paths for no retrieved result, conflicting memories, a stale graph, a truncated walk, and an ambiguous request. The UI should narrow its claim, offer a clarification or fallback, and preserve the distinction between “no evidence found” and “the fact is false.” | [Microsoft HAX G10, scope when in doubt](https://www.microsoft.com/en-us/haxtoolkit/guideline/scope-services-when-in-doubt/); [Google People + AI, Errors + Graceful Failure](https://pair.withgoogle.com/chapter/errors-failing/) |
| Correction and control | Let a user flag an individual result as wrong, inspect its basis, correct or quarantine it through an understandable action, and see the effect of that action. Test that a failure has a manual path to continue the task. | [Microsoft HAX G15, granular feedback](https://www.microsoft.com/en-us/haxtoolkit/guideline/encourage-granular-feedback/); [Google People + AI, Feedback + Control](https://pair.withgoogle.com/chapter/feedback-controls/); [Google People + AI, Errors + Graceful Failure](https://pair.withgoogle.com/chapter/errors-failing/) |
| Recovery | For indexing, recall, sync, or evidence failures, distinguish in-progress, partial, failed, and recovered states. Explain what the user can retry and what data remains available. Evaluate these with scenario walkthroughs, not only a happy-path screenshot. | [Microsoft HAX Playbook](https://www.microsoft.com/en-us/haxtoolkit/playbook/); [Carbon empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/) |

## Evidence to collect during the product audit

For each sampled journey, record viewport and theme, keyboard sequence, screen-reader announcement where relevant, screenshot, observed text/state, expected criterion above, and severity based on blocked task or misleading decision. Suggested journeys: first-run setup; browse/search/filter; inspect a graph node and source; inspect memory evidence and scope; handle empty or conflicting results; respond to stale or partial index; correct a bad result; switch theme and zoom. Standards failures should identify the exact WCAG success criterion. Design guidance gaps should be labelled as recommendations.
