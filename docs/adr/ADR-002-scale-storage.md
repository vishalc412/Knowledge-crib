# ADR-002 — Scale storage: single soul vs per-module souls, lazy shard loading, dossiers-in-git

- **Status:** Accepted
- **Date:** 2026-07-13
- **Milestone:** M3.6 (scale measurement)
- **Supersedes:** the M3.6 plan row's open question — "decide per-module souls / lazy shard loading from data, not guesswork. Include dossiers-in-git decision (22 MB of 43 MB committed)."

## Context

The plan's M3.6 row left three storage decisions open until measured data existed:

1. **Per-module souls** — should the soul (the committed graph) be one blob for the whole repo, or split per package (monorepo) / per module?
2. **Lazy shard loading** — should the server/index load only the shards a query touches, or the whole soul?
3. **Dossiers-in-git** — the committed `.crib` is ~44 MB / 2,279 files, of which 1,834 are dossiers (the bulk). Are dossiers a committed artifact or derived state?

All three turn on the same property: **how does `crib index`'s peak memory grow with corpus LOC?** If the pipeline streams (per-file extract → persist → discard) and the sqlite index is disk-backed, peak RSS is bounded regardless of corpus size → a single soul is fine, lazy loading is unnecessary, and the only question is dossier cost. If peak RSS grows with LOC (state accumulating in memory), per-module souls + lazy shard loading are warranted at enterprise scale.

This ADR answers from the measured curve in `docs/bench/scale-curve.md` (generated by `scripts/scale-bench.mjs`), not guesswork.

### The measured curve

Method: the 23-file `packages/parsers/fixtures` tree (~877 LOC, spanning every supported extractor's surface) replicated into N sibling `batchN/` dirs → N×877 LOC of real extracted code, indexed by the built `crib` CLI under `/usr/bin/time -l` (which reports both wall seconds and peak RSS for the child). Setup is excluded; only the `crib index` run is timed. This mirrors the M3.4 replicated-fixture precedent (the 23-file fixture is too small to amortize anything, so it is scaled). `--repo <path>` adds a real-repo full-index cross-check point.

The committed curve (`docs/bench/scale-curve.md`, regenerated by `scale:nightly`) measured three points on this machine (18 GB RAM, Apple Silicon, Node 25):

| LOC | Files | Nodes | Wall (s) | Peak RSS (MB) | MB/kLOC | Nodes/s |
|---:|---:|---:|---:|---:|---:|---:|
| 10,524 | 252 | 5,853 | 10.63 | 327 | 31.1 | 551 |
| 25,433 | 609 | 14,113 | 51.81 | 573 | 22.5 | 272 |
| 50,866 | 1,218 | 28,209 | 184.97 | 678 | 13.3 | 153 |

A 200K-LOC slice was started and **terminated after 18 min CPU** (still running) — vs 37 s at 20K LOC, a ~29× slowdown for 10× the data. It did not complete; it is recorded here as the qualitative endpoint confirming super-linear index time.

### What the curve says — two different shapes

**Peak RSS is SUB-LINEAR (memory is bounded).** MB/kLOC *declines* with LOC: 31.1 → 22.5 → 13.3. RSS rises 327 → 573 → 678 MB — a large fixed baseline (~250–300 MB: Node + V8 + sqlite + tree-sitter grammars + cluster init) plus a small, *shrinking* marginal rate (~4 MB/kLOC between the last two points). A sqrt-fit extrapolation puts a 1M-LOC single-soul index at ~3 GB peak RSS — feasible on a 16–32 GB developer machine. The pipeline streams (per-file extract → persist → discard) and the sqlite index is disk-backed, exactly the property the plan's "lazy shard loading" question was probing for. **The data says memory is NOT the bottleneck.**

**Index TIME is SUPER-LINEAR (~N^1.8) — time IS the bottleneck.** Wall rises 10.6 → 51.8 → 185 s; a power-law fit gives `time ≈ a · LOC^1.81` (near-quadratic). Throughput (nodes/s) *halves* roughly every 2× LOC: 551 → 272 → 153. Extrapolated to 1M LOC, a single-soul index is ~11 hours. The 200K stall confirms it. The super-linear phase is the link/resolve + Louvain cluster work over the growing node set — work that operates on the *whole* graph, not per-file.

This flips the naive guess. The plan framed per-module souls / lazy shard loading as a *memory* mitigation. The data says memory is fine; **the real scale cost is index TIME, and it is super-linear in whole-graph node count.**

## Considered options

### Option A — Single soul, eager full load (status quo)

The whole repo's graph is one soul (`.crib/soul/`), loaded in full at server/index startup. This is crib's current shape. Simplest; query-time joins across packages are trivial (one graph in memory). The risk is peak RSS at scale: if RSS grows with LOC, a 1M-LOC repo may not fit in memory on a 16–32 GB developer machine.

### Option B — Per-module souls + lazy shard loading

Split the soul per package (monorepo) or per module directory. The server lazy-loads only the shards a query touches (by id-prefix → shard file). Cross-package joins resolve via a shard index (a small manifest of which shard holds which node id). Pro: peak RSS bounded by the largest shard, not the whole repo. Con: cross-package queries need multi-shard fan-out; the deterministic commit/diff story is per-shard (merge driver already handles chunk-level merges, so this composes); a shard manifest must stay in sync.

### Option C — Single soul, lazy load (shards within one soul, loaded on demand)

Keep one soul logically, but partition its chunks into shard files the loader fetches by id-prefix on demand. Hybrid of A and B: one logical graph, bounded RSS, no cross-package fan-out (the loader hides sharding). Con: the loader must know which shard file holds each id; partial loads complicate `--extracted-only` byte-identical determinism (the committed set must still be the full soul).

## Decision

### Per-module souls — YES, driven by INDEX TIME (not memory)

**Split the soul per package (monorepo) / per top-level module.** The super-linear `~N^1.8` index time is the decisive cost, and it operates on *whole-graph* node count (link/resolve + Louvain cluster). Splitting the soul bounds N per module: a 1M-LOC repo as 10 modules of ~100K LOC each costs `10 × time(100K)` ≈ 10 × ~10.5 min = ~105 min **sequential**, or ~10.5 min **parallel** (modules index independently, no cross-module edges until a federation layer resolves them) — vs ~11 h for a single 1M-LOC soul. That is a **6–60× wall-clock win**, bought by keeping the super-linear phase operating on per-module N instead of whole-repo N.

This is a TIME decision, not a memory decision — the curve explicitly ruled memory out (sub-linear RSS, ~3 GB projected at 1M). The split composes with the existing chunk-level merge driver (per-module souls are just more chunks) and with the M3.2 federation layer (cross-repo route bridge already resolves A→B at runtime; cross-module within-repo resolution is the same mechanism one level down).

### Lazy shard loading — DEFER (not warranted by data)

**Do not build lazy shard loading now.** The plan listed it as a candidate memory mitigation, but the curve shows peak RSS is sub-linear and bounded (~3 GB projected at 1M) — there is no memory pressure demanding it. Building lazy loading now would add a shard-manifest + partial-load machinery (with its own `--extracted-only` byte-identical-determinism risks) for no measured benefit. **Revisit if the memory shape changes materially** (re-run `scale:nightly` when the pipeline changes; the `scale:check` gate pins the harness). The per-module-soul split already gives most of lazy loading's hypothetical benefit for free (a query touches one module's soul → only that shard is loaded), without a dedicated manifest.

### Dossiers-in-git — KEEP committed

**Decision: dossiers stay committed in `.crib/dossiers/`.** They are NOT derived state and must not be gitignored.

Reasoning:

- **Dossiers are non-deterministic.** They are LLM-generated deep artifacts (rehydrated source body + callers/callees + decision table + CFG constructs). LLM output varies run-to-run, so a dossier is NOT rebuildable byte-identically from the soul the way `.crib/index/` (sqlite) is. Gitignoring dossiers would make the deep context unreproducible — `git checkout <commit>` would no longer yield the same dossiers.
- **Dossiers are expensive.** Each dossier costs an LLM call (the `crib enrich` loop + the `/crib-enrich` skill). Regenerating the fleet on every clone would burn the LLM budget for a graph that already exists. Committing preserves the LLM investment.
- **Dossiers are grounded + audited.** `crib audit-llm` re-verifies every dossier against the soul and exits non-zero on drift — the grounding moat. A committed dossier that drifts from the soul is caught at the gate, not silently trusted. This makes committing them safe: the integrity invariant is enforced by audit, not by "regenerate to be sure."
- **The cost is bounded and acceptable.** Committed `.crib` is ~44 MB for this repo. A knowledge graph repo where the graph IS the product is the one place a few tens of MB of committed JSON is the *right* trade — it is the artifact, not build output. The gitignored set stays the truly derived state (sqlite index, embeddings): `.crib/index/`, `.crib/embeddings/`, `.crib/.lock`.

The line is therefore: **commit the non-deterministic expensive grounded artifacts (soul + dossiers); gitignore the deterministic cheap rebuildable ones (sqlite index, embeddings).** This is the opposite of the naive "commit nothing derived" rule, and it is correct here because the deterministic things are cheap to rebuild while the non-deterministic things are not.

## Consequences

- **Per-module souls are the M3.6+ implementation work** (out of M3.6's scope to *build*; this ADR is the decision). The split must preserve `--extracted-only` byte-identical determinism (a whole-repo `--extracted-only` run must still produce the same extracted edge set as the union of per-module runs) and compose with the chunk merge driver + M3.2 federation. The cluster (Louvain) must run per-module; cross-module clustering is deferred to a federation layer if ever needed.
- **Lazy loading is explicitly NOT built** — recorded here so a future contributor doesn't add it on the guess that "scale needs it." The data says it doesn't. Re-running `scale:nightly` is the trigger to revisit.
- **Index time, not memory, is the scale to watch.** A future O(N) link/cluster algorithm would flatten the time curve and could change this decision (a single soul becomes cheap again). Until then, per-module souls are the mitigation.
- The `crib audit-llm` gate is load-bearing for dossier integrity and stays in release:verify.
- `--extracted-only` byte-identical determinism is unaffected by the dossier decision (dossiers are INFERRED-layer, not EXTRACTED; the extracted edge set is unchanged by their presence).
- `scripts/scale-bench.mjs` + `scale:check` (release:verify smoke, 20K-LOC slice) + `scale:nightly` (full 1M-LOC curve) pin this decision: re-run the bench when the pipeline changes; this ADR is revisited if the RSS-per-kLOC shape turns super-linear or the time exponent drops below ~1.3.
