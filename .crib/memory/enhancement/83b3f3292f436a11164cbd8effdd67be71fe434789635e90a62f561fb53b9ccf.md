## The claim, in one line

"freshness.behindHead requires a PUBLISHED generation — index/update never publish"

## How to apply it

When you need the stale-index state to exist — to make any path that keys off it reachable, or to see
`behind HEAD: yes` in `crib freshness status` — do not try to reach it by indexing. Reproduce the
record's recipe as written: with `.crib` already present, run `crib freshness auto`, then
`crib freshness hook`, start the worker (`crib freshness worker`) and let it publish a generation,
then stop the worker and `git commit`. The status surface that then reads `behind HEAD: yes` is the
no-args branch of `cmdFreshness` at `packages/cli/src/cli.ts:3929`, whose `last-known-good:` and
`behind HEAD:` fields (including the literal `never published` for an absent generation) are the
strings to watch.

When a repair line points you at `crib update` (or `crib index`) to clear this condition, do not
treat that as sufficient: publication is worker-only — the publisher's `publishGeneration` call sits
at `packages/cli/src/freshness.ts:943` inside `FreshnessWorker.run` — so drive repair through the
worker and re-read the status line rather than assuming a re-index moved it.

In a test, induce the state the way the existing suite does rather than by indexing: the shape is in
`packages/cli/src/freshness.test.ts:453` (a direct `publishGeneration` with a generation whose `head`
is `h0`), asserted at `:466` as `expect(s.behindHead).toBe(true); // published at h0, current HEAD is
h1`. Its negative control is at `:471`, where an unregistered project with no published generation
reports `behindHead: false`. Copy that pair of shapes; do not hand-set `lastKnownGood`.

## What would falsify it

A second call site of `publishGeneration` in `packages/cli/src` reachable from `crib index` or
`crib update` — the record's `publishGeneration` call has exactly one call site, at
`packages/cli/src/freshness.ts:943` inside `FreshnessWorker.run`. A `crib freshness status` run in a
repo where only `crib index`/`crib update` were ever run that prints `last-known-good: <generation>…
@ <head>` instead of `never published`. A `behind HEAD: yes` reading in a repo whose last-known-good
was never published, which would break the guard at `packages/cli/src/freshness.ts:1123`
(`behindHead: last !== undefined && head !== undefined && last.head !== head,`) inside
`freshnessStatus`. Or a post-commit hook that enqueues in `manual`/`watch`, contradicting the hook
line at `packages/cli/src/cli.ts:3887` ("enqueue in `auto`, no-op otherwise").

## Scope — what this does NOT claim

It does not claim that `crib index` or `crib update` fail to refresh the graph — only that they cannot
move the published generation, so `behindHead` stays as it was. It does not claim the generation files
have no other writer in any path; the claim is about `publishGeneration`'s call sites. It does not
claim `behindHead` can never be true: "permanently false until a generation is published" describes
the unpublishable window, and the record's own recipe induces the true state once a generation exists.
