## The claim, in one line
"The x-dc component payload in packages/ui/web/index.html cannot be extracted to a <script src> module"

## How to apply it

Read the runtime's own reader before acting on any "move this logic into a module" instruction. The deciding lines are `packages/ui/web/support.js:27` and `:45`, both `const scriptEl = doc.querySelector("script[data-dc-script]");`, and the payload they find is the `<script type="text/x-dc" data-dc-script data-props="…">` tag at `packages/ui/web/index.html:726` (its document block is `<x-dc>` at `index.html:17` through `</x-dc>` at `:725`). If the code you were told to move lives inside that tag, stop: a `<script src>` file is not in the served document, the query returns null, and the failure path at `support.js:1372` reports the document "has no <x-dc> block". Do not reach for `support.js` instead — its line 1 begins `// GENERATED from dc-runtime/src/*.ts — do not edit.` and carries the rebuild command `cd dc-runtime && bun run build`, and no `dc-runtime/` tree exists here to rebuild it from.

Do the extraction the repo has a precedent for. `packages/ui/web/graph-model.js` was already carried out of this component and is loaded at `index.html:13` by `<script src="./graph-model.js">`, exposing `root.KCGraphModel` (the `root.KCGraphModel = {` export assignment at `graph-model.js:252`). Apply its rule: move only methods that are `this`-free and read neither component state nor the DOM. Four were moved on exactly that rule — `hex` (`graph-model.js:197`), `esc` (`:212`), `ellipsize` (`:227`), `rr` (`:242`). Re-test in two commands: `grep -oE 'KCGraphModel\.(hex|esc|ellipsize|rr)\(' packages/ui/web/index.html | wc -l` must print 34, and `grep -nE '^\s*(function|const|let|var)\s+(hex|esc|ellipsize|rr)\s*[=(]' packages/ui/web/index.html` must print nothing.

## What would falsify it

Three observations, each makeable here. (1) The structural clause falls if the queried payload can arrive by a route other than the served markup — e.g. if `support.js` were changed to fetch the module and inject it into the document before the read at `support.js:27`, `<script src>` extraction becomes available. (2) The "support.js is not an escape" clause falls if `ls dc-runtime/src` succeeds and `cd dc-runtime && bun run build` reproduces `packages/ui/web/support.js` byte-for-byte, making the file editable through its generator. (3) The impossibility clause falls if the `data-dc-script` tag is removed from `index.html`, a `<script src>` module takes over, and the canvas still boots — the query at `support.js:27` is then no longer the boot path.

## Scope — what this does NOT claim

Do not read the subject as "index.html's inline logic cannot be extracted", nor as "WP3-H4 failed". The record's narrow target is one mechanism: content behind `<script src>` is absent from the served document. It does not claim the payload is untestable, and it does not claim `support.js` contains anything wrong — only that it cannot be edited here because its generator is absent. It does not claim the DC runtime generally cannot load from a module; it claims this build reads the component out of the document by that query. Nor are the four moved methods asserted to be the only movable ones: the rule is stated, not the class of all methods satisfying it.
